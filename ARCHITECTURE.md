# RelayOS architecture

RelayOS is currently a static React application that demonstrates repository structure and the approved-knowledge boundary. It has no backend, persistence, identity, document ingestion, or model integration. Planned architecture below describes constraints for later execution plans, not Phase 0 features.

## Current system

Vite builds a client-side React/TypeScript SPA for Cloudflare Pages. React Router owns navigation, and a static fallback lets direct route requests reach the SPA. Domain code is framework-free; the first primitive decides whether a knowledge item may be employee-visible. `src/demo/` is reserved for deterministic no-API behavior.

Dependencies point inward: application and feature code may use domain and shared code; domain code must not import React or infrastructure. External adapters belong in `src/infrastructure/` only when an execution plan introduces a real boundary. Avoid interfaces, repositories, or services with no current caller.

## Planned operating loop

```text
employee question
  -> retrieve approved company knowledge
  -> answer or escalate
  -> identify a knowledge gap
  -> draft a proposed system improvement
  -> owner reviews it
  -> approved knowledge becomes available in the future
```

The proposal and the resulting approved knowledge are distinct records. Approval never rewrites an item’s origin, and a generated answer does not become policy. See [data flow](docs/architecture/DATA_FLOW.md) and [domain model](docs/architecture/DOMAIN_MODEL.md).

## Normative system rules

These rules are architectural acceptance criteria. Later storage, APIs, UI, and tests must enforce them at every write and read boundary.

| #   | Rule                                                                                                                                   | Required enforcement                                                                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 1   | Employee-visible answers may use only approved knowledge.                                                                              | Domain visibility policy plus server-side retrieval filtering; reject mixed-status evidence. |
| 2   | Generated or inferred content must remain visibly unapproved.                                                                          | Preserve origin and approval state in storage and UI; generation cannot set approval.        |
| 3   | Every approved knowledge item must retain its source and approval history.                                                             | Publishing requires source references and an approval decision; both remain addressable.     |
| 4   | When evidence is absent, conflicting, sensitive, or below confidence thresholds, RelayOS must escalate instead of inventing an answer. | Deterministic eligibility checks produce an escalation and knowledge gap.                    |
| 5   | Approval history is append-only.                                                                                                       | Decisions are immutable events; corrections append decisions or create revisions.            |
| 6   | Independence scores must be derived from visible components, not generated by a language model.                                        | Versioned deterministic formula with inspectable inputs and tests.                           |
| 7   | No API secret may exist in browser code.                                                                                               | Build/config review and secret scanning; browser receives only public configuration.         |
| 8   | Model providers must be accessed through a server-side `ModelGateway` abstraction in a later phase.                                    | No provider SDK or call in client/domain code; gateway boundary owns provider access.        |
| 9   | The application must support a deterministic no-API demonstration mode.                                                                | Fixed fixtures/adapters, seeded outcomes, and tests independent of network/model access.     |
| 10  | The first version supports one company and one role well before supporting generalized multi-tenancy.                                  | Scope every domain record to that company/role without building tenant administration.       |

Rule 2 means generated answers may be shown only as grounded responses assembled exclusively from approved knowledge, with citations and an explicit generated/non-policy label. They are never silently promoted into reusable knowledge. Rule 4 takes precedence whenever grounding eligibility fails. More detail is in [AI boundaries](docs/architecture/AI_BOUNDARIES.md).

## Knowledge states and traceability

- **Source material** is captured as a `SourceDocument` and cited through immutable `SourceReference` locators.
- **Extracted claims** remain candidates until an owner decision; extraction is not approval.
- **Generated proposals** preserve their generated origin and referenced evidence.
- **Owner-approved knowledge** is an immutable revision with sources and an append-only `ApprovalDecision` history.
- **Rejected knowledge** is retained with its rejection decision and never retrieved as approved.
- **Missing or conflicting information** produces a `KnowledgeGap` and escalation, not a synthetic claim.

## Hosting and later boundaries

Phase 0 deploys only static assets. Cloudflare Workers, D1, R2, KV, authentication, and secrets are intentionally absent. Before introducing model calls or protected company information, a later plan must add a server trust boundary, authorization, durable audit/provenance storage, and the `ModelGateway` described in [security](docs/architecture/SECURITY.md).
